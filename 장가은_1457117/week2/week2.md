## 📅 26.01.12 (월) — WebRTC 개념과 “왜 필요한가” 이해하기

이번 학습에서는 WebRTC를  
**“웹에서 실시간 통신을 가능하게 하는 기술”**이라는 관점에서 큰 그림부터 정리했다.

기존의 실시간 음성·영상 통신은 전용 프로그램 설치나  
특정 플랫폼에 종속되는 경우가 많았다.  
반면 **WebRTC(Web Real-Time Communication)** 는  
별도의 플러그인 없이도 **브라우저 기반 실시간 통신**을 가능하게 하는 기술이다.

WebRTC는 오픈소스 프로젝트로 출발했으며,  
주요 브라우저에서 기본적으로 지원되는 **JavaScript API** 형태로 제공된다.  
이로 인해 개발자는 특정 벤더 기술에 의존하지 않고  
표준 방식으로 실시간 통신 기능을 구현할 수 있다.

또한 브라우저뿐 아니라 Android / iOS 환경에서도  
동일한 통신 모델을 확장할 수 있어,  
하나의 기술로 다양한 플랫폼을 아우를 수 있다는 장점이 있다.

### 🔑 WebRTC의 핵심 특징

WebRTC의 가장 중요한 특징은  
**P2P(Peer-to-Peer) 기반 통신을 기본 구조로 사용한다는 점**이다.

- 연결이 성립된 이후에는 참가자 간 직접 통신
- 서버가 모든 미디어 트래픽을 중계하지 않음
- 지연 시간이 짧고 서버 비용 부담이 적음

이 구조는 화상 채팅, 실시간 영어 회화, 협업 음성 채팅처럼  
**즉각적인 반응성이 중요한 서비스**에 적합하다.

다만 “서버 없이 동작한다”는 표현은 오해의 소지가 있다.  
실제로는 **연결이 성립되기 전 단계에서 반드시 서버가 필요**하며,  
이 과정을 **시그널링(Signaling)** 이라고 한다.

#### 📌 Day1 핵심 정리
- WebRTC는 브라우저 기반 실시간 통신을 지원하는 표준 기술이다.
- 연결 이후에는 P2P로 통신해 실시간성과 효율이 뛰어나다.
- 연결을 시작하기 위한 정보 교환 단계에서는 시그널링 서버가 필요하다.

## 📅 26.01.13 (화) — 연결이 만들어지는 과정: Signaling · SDP · ICE

Day2에서는 WebRTC 연결이  
**어떻게 실제로 성립되는지**를 구성 요소별로 정리했다.

WebRTC 연결은 단순히 `RTCPeerConnection()`을 생성한다고 끝나는 것이 아니라,  
미디어 정보와 네트워크 경로를 서로 협상하는 과정을 거친다.

이때 핵심이 되는 개념이  
**Signaling / SDP / ICE** 이다.

---

### 1️⃣ Signaling — 연결을 시작하게 만드는 단계

WebRTC는 시그널링 방식을 특정 기술로 강제하지 않는다.

- WebSocket
- HTTP API
- 기타 메시징 방식

중요한 것은 **역할**이다.

Signaling은 다음을 담당한다.

- 피어들이 서로를 찾도록 연결
- 연결에 필요한 정보 교환
- P2P 연결 시작을 위한 중개

비유하자면 **소개팅 주선자** 역할이다.  
연결 전 단계에서는 반드시 서버가 필요하며,  
이 서버가 시그널링 서버로 동작한다.

---

### 2️⃣ SDP(Session Description Protocol) — 세션 정보 교환

SDP는 세션에서 사용될 미디어 정보를 담은 텍스트 형식이다.

- 지원하는 오디오/비디오 코덱
- 해상도 및 미디어 설정
- 트랙 정보

연결 과정에서는 다음 흐름으로 협상이 이루어진다.

- 한쪽이 **Offer SDP** 생성
- 상대방이 이를 기반으로 **Answer SDP** 응답

이 과정을 통해  
서로가 공통으로 지원 가능한 최적의 미디어 설정을 결정한다.

개발자가 SDP를 직접 수정할 일은 많지 않지만,  
**Offer / Answer 구조가 존재한다는 점은 WebRTC의 핵심 원리**다.

---

### 3️⃣ ICE(Interactive Connectivity Establishment) — 연결 경로 탐색

ICE는 실제로  
**어떤 네트워크 경로로 연결할지 결정하는 프레임워크**다.

대부분의 사용자는 NAT 뒤에 있기 때문에  
단순한 IP 연결만으로는 직접 통신이 어렵다.

ICE의 역할은 다음과 같다.

- 가능한 연결 후보(ICE Candidate) 수집
- 각 후보의 연결 가능성 테스트
- 가장 안정적이고 지연이 낮은 경로 선택
- 직접 연결이 불가능할 경우 릴레이 방식 고려

#### 📌 Day2 핵심 정리
- WebRTC 연결은 자동으로 되는 것이 아니다.
- Signaling으로 SDP를 교환하고,
- ICE를 통해 실제 연결 경로를 협상해야 한다.

## 📅 26.01.14 (수) — NAT 환경 문제 해결과 확장 구조 이해

Day3에서는  
**현실적인 네트워크 환경에서 WebRTC가 부딪히는 문제**를 다뤘다.

핵심은  
**왜 STUN/TURN이 필요한지**,  
그리고 **왜 SFU/MCU 구조가 등장하는지**였다.

---

### 1️⃣ STUN & TURN — NAT 환경 문제 해결

#### STUN (Session Traversal Utilities for NAT)

- 외부에서 보이는 나의 Public IP/Port 확인
- ICE 후보에 포함해 상대에게 전달
- 가볍고 빠른 방식

#### TURN (Traversal Using Relays around NAT)

- STUN으로도 직접 연결이 불가능할 때 사용
- 서버가 미디어를 중계(릴레이)
- 성공률은 높지만 서버 비용과 지연 증가

👉 WebRTC의 기본 전략은 다음과 같다.

1. STUN으로 직접 연결 시도
2. 실패 시 TURN 서버를 통한 릴레이 사용

---

### 2️⃣ WebRTC 전체 동작 흐름

1. 시그널링 서버를 통해 연결 시작
2. Offer / Answer(SDP) 교환
3. ICE 후보 수집 및 경로 탐색
4. 최적 경로로 P2P 연결 성립
5. 연결 이후에는 시그널링 서버 없이 직접 미디어 전송

---

### 3️⃣ P2P 구조의 한계와 SFU / MCU

P2P 구조는 참가자가 늘어날수록  
연결 수가 **N(N-1)/2**로 증가한다.

이는 클라이언트의  
CPU·네트워크 부담을 급격히 증가시킨다.

이를 해결하기 위해 등장한 구조가 다음과 같다.

- **SFU (Selective Forwarding Unit)**
  - 서버가 스트림을 전달만 수행
  - 확장성과 지연 측면에서 균형이 좋음
- **MCU (Multipoint Control Unit)**
  - 서버가 스트림을 합성해 전달
  - 클라이언트 부담은 적지만 서버 비용 큼

서비스 규모와 품질 요구에 따라  
구조 선택이 중요하다는 점을 이해했다.

## 📅 26.01.15 (목) — WebRTC 기반 서비스 기획안 작성

이번에는 WebRTC 개념을  
**실제 서비스 기획으로 연결**하는 작업을 진행했다.

기술 자체보다  
**“왜 이 기술을 쓰는가”**,  
**“사용자에게 어떤 가치를 주는가”**에 집중했다.

### 🔑 기획 핵심 포인트

- 실시간성이 핵심인 서비스 정의
- 사용자 흐름 기반 설계
- WebRTC 선택 이유 명확화
- 향후 확장(SFU) 가능성 고려

이를 통해  
WebRTC는 기술 그 자체보다도  
**문제 해결을 위한 선택이라는 점**을 체감했다.
